> Companion note for `docs/09-audio-and-pronunciation.md`. That document decides how German audio must sound. This document only explains how to check which speech services are reachable, and how to do it without ever revealing a key.

# Speech Provider Operations

## What this is for

The learning platform speaks German. Every spoken clip a learner hears is a sound
file that was produced once, listened to by a person, and saved. Nothing is
spoken "live" while a learner is using the app.

Four speech services are recorded in this project:

| Service | Role | Needs a key? | What it is used for |
|---|---|---|---|
| `edge-tts` | approved main voice | no | The 327 German clips that already exist. Voice `de-DE-KatjaNeural`, speaking rate `+4%`. |
| `cartesia` | comparison | yes | Listening to how a paid service reads the same German, if we ever want to compare. |
| `openrouter` | stand-in | yes | A possible temporary source if the main voice stops working. |
| `ttsforfree` | comparison | yes | A low-cost service whose key can be checked through its published read-only API. |

Only `edge-tts` is approved. The other three exist so that a decision can be
made with evidence instead of guessing. None of them may replace the approved
voice without a recorded decision (see `docs/DECISIONS.md`, ADR-005).

## The production strategy for this Alpha

This Alpha has three users. That makes the simplest approach also the best one:

**Generate each clip once, have a person listen to it, save the file, and serve
that saved file forever.**

Consequences of that choice, all of them deliberate:

- learners never wait for a speech service, so playback starts immediately;
- the app keeps working offline;
- a service outage, a price change or an expired key cannot break a lesson;
- no key is ever needed by the app itself, so no key can leak from it.

A speech service is therefore only ever contacted by a person at a keyboard,
during preparation work, never by the app while somebody is learning.

## Where keys live

There are exactly two files, and both live outside this project folder:

1. `E:\claude-cursor\central-home\secrets\.secrets.env` — shared across your
   machine. **Do not edit this file for this project.**
2. `E:\claude-cursor\central-home\secrets\german-learning-tts.env` — belongs to
   this project. This is the only file you edit.

`config/tts-providers.env.example` in this project shows the setting names with
empty values. It is a template. Never put a real key in it, and never put a real
key anywhere inside this project folder.

If the same setting appears in both files, the project file wins — unless it is
left blank, in which case the shared value is used. Anything already set in your
terminal session wins over both files.

## How to add a key (no technical knowledge needed)

1. Get the key from the service's own website, from your own account.
2. Open `E:\claude-cursor\central-home\secrets\german-learning-tts.env` in a text
   editor.
3. Find the line for that service and type the key after the `=` sign, with no
   spaces and no quotation marks. For example the Cartesia line becomes
   `CARTESIA_API_KEY=` followed immediately by the key.
4. Save the file and close the editor.
5. Run the check in the next section. It will tell you whether the service
   accepted the key.

Leaving a line blank is completely fine and is the normal state. A blank line
means "not supplied yet", and the check reports that service as
`not_configured` rather than treating it as broken.

Two optional settings are worth knowing about:

- `TTSFORFREE_API_BASE` — normally leave this blank. For key safety, the check
  currently accepts only the documented `https://api.ttsforfree.com` host and
  refuses to send a key anywhere else. A future migration requires a reviewed
  code change, not just an environment edit.
- `CARTESIA_VOICE_ID` — which Cartesia voice to compare against, only needed if
  Codex asks for a comparison.

## How to run the check

Open a terminal in the project folder and run:

```bash
python -m tools.tts.smoke
```

Useful variations:

```bash
python -m tools.tts.smoke --offline          # check only the local setup, contact nobody
python -m tools.tts.smoke --strict           # also fail loudly when anything is unhealthy
python -m tools.tts.smoke --allow-generation # additionally speak one short free sample
```

The check writes a report to `research/tts-provider-smoke.json` and prints a
short summary. The report contains statuses, not secrets.

What the check does:

- confirms the `edge-tts` software is installed and still offers `de-DE-KatjaNeural`;
- asks OpenRouter whether each supplied key is accepted, using the account page
  that reports remaining credit, and lists which OpenRouter models can return
  audio at all — with the warning that some of those generate music rather than
  read German aloud, so the list is a shortlist for Codex to listen to, not an
  approved option;
- asks Cartesia for one voice from its voice list, which costs nothing;
- checks a TTSForFree key using `GET /api/Common/GetListLanguage` and the
  documented `X-API-Key` header; it does not generate speech;
- counts the approved clips already on disk and confirms their file names are
  still reproducible.

What the check never does:

- pay for anything, or generate any learner audio;
- print or save a key, a partially masked key, or an account identifier;
- touch the publisher's coursebook or workbook audio;
- change, regenerate or delete any of the 327 approved clips.

`--allow-generation` is the one exception to "no audio is produced", and it is
narrow on purpose: it speaks a short phrase with the free local `edge-tts`
software only, within a character limit (40 by default), writes it to a temporary
file, confirms the result really is audio, and deletes it. The paid services are
never asked to generate anything, regardless of flags.

## How to read the result

Each service gets one status word:

| Status | Meaning | What to do |
|---|---|---|
| `available` | Working right now. | Nothing. |
| `not_configured` | No key supplied. | Nothing, unless you want that service. |
| `skipped_offline` | A key exists but you asked for an offline check. | Re-run without `--offline`. |
| `unauthorized` | The service rejected the key. | Replace the key with a current one. |
| `quota_limited` | The key is valid but out of credit, or too many requests were made. | Wait for the reset, or add credit. Do not add a second key to get around the limit. |
| `endpoint_unknown` | A key exists but we have no address for the service. | Add the address from the provider's documentation. |
| `network_unreachable` | The service could not be contacted. | Check the internet connection. |
| `provider_error` / `unexpected_response` | The service answered in a way we do not trust. | Try again later; do not treat it as working. |
| `tool_missing` | Software is not installed. | Install `edge-tts` for this Python installation. |

The last lines of the summary give the overall result:

- `ok` — the approved voice works and nothing needs attention;
- `degraded` — the approved voice works, but something optional needs a look;
- `failed` — the approved voice is not usable; existing clips still play, but new
  clips have to wait;
- `configuration-error` — a setting is wrong or contradicts the approved
  decision. Fix that first; nothing else in the report should be trusted.

The command finishes quietly (exit code `0`) even when an optional service is
missing, because a missing optional service is not a problem. It ends with an
error only for a broken configuration (`2`) or if it detected something
key-shaped in its own output and refused to write the report (`3`). Add
`--strict` if you want anything less than `ok` treated as a failure.

## How a provider gets selected

The answer is normally short: **`edge-tts`, because it produced the clips that
are already reviewed and cached.**

The summary line `Use for new audio:` names the service to use for any *new*
clip. It only names something other than `edge-tts` when the approved voice is
genuinely unavailable, and even then the report says plainly that any clip from a
different service needs a fresh listening review before a learner hears it.

Nothing switches voices automatically. A different service can only be adopted
by a person, after a listening review, and after a decision record is written.

### Why a fallback cannot damage existing audio

Every clip's file name is derived from everything that affects how it sounds:
the exact text, the language, the voice, the service, the model version, and the
speaking controls (rate, pitch, volume), plus the audio format.

Because the service and voice are part of that recipe, a clip made by a
different service always lands on a *different* file name. It is stored beside
the approved clip, never on top of it. The approved clips keep the exact names
they already have, so nothing that already works can be quietly replaced. The
check verifies this every run by recomputing the names of all approved clips and
comparing them with the audio manifest.

## Rules that are not negotiable

1. `edge-tts` stays the main voice for Alpha; existing audio is never
   regenerated.
2. The other three services are for comparison or for covering an outage.
3. Having several keys is allowed for resilience only. Cycling keys to get more
   free capacity than a service grants to one account is not allowed, and each
   service's own terms apply to its own key.
4. No key ever goes into the app, the browser, a published file, a report, a log
   or a screenshot. The app does not need one, because it plays saved files.
5. Keys are read only from the two files named above. The shared file is never
   modified by this project's tooling, and blank lines in the project file are
   left exactly as the owner left them.
6. The publisher's own coursebook and workbook audio is untouched by all of this.
   It stays in the private source lane until `redistributionBasis` records a
   permission (ADR-011).
7. If something is unknown — an unrecognised service name, a missing key, a
   model that cannot speak, or an answer that is not audio — the tooling reports
   a clear error and produces no success report. It never guesses.

```bash
python -m unittest discover -s tests/tts-tools -p "test_*.py"
```
